# 目的発見

## 目的

解決策ではなく、解決したい問題と成功条件を確認する。

## 読むタイミング

最初の確認質問を出す直前。依頼が曖昧、広すぎる、急ぎを理由に質問省略が求められる場合も含む。

## 手順

1. **1回に1問を基本にする**
   - 次の判断に必要な最小の未確定事項だけを聞く。
   - 回答を受けてから次の質問を決める。質問票を一括で消化しない。
2. **5W1Hを入口にする**
   - まず目的、利用者、利用状況、成功条件、制約のうち最も欠けている点から入る。
3. **Why と現状を掘る**
   - なぜ必要か、今は何で代用しているか、失敗時に何が困るか、成功の兆候は何かを順に深掘りする。
4. **解決策と事実を分ける**
   - ユーザーが先に解決策を出していても、それを事実として扱わず、背景の目的を確認する。
5. **照合して止まる**
   - 事実 / 仮説 / 未確定事項を短く要約し、ユーザー確認を得るまで設計や成果物作成へ進まない。

## 出力の形

- **事実**: ユーザーが明示した内容、確認できた制約、既知の既存資産
- **仮説**: まだ検証していない意図、候補ドメイン、想定利用者
- **未確定事項**: 次に聞くべきこと、調査で確かめるべきこと

必要なら、この時点の合意内容を [../templates/requirements.md](../templates/requirements.md) に記録する。
