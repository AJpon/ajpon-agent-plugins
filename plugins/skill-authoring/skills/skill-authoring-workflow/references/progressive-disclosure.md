# 段階的開示と構成設計

## 目的

`SKILL.md` を司令塔に保ち、詳細を必要な参照資料とテンプレートへ分ける。

## 読むタイミング

ファイル構成、責務分担、読込条件を設計し、レビュー用の構成案を作る直前。

## 設計ルール

1. **`SKILL.md` は lean orchestrator**
   - 持つのは、トリガー、順序、承認ゲート、停止条件、各参照資料を読むタイミング、引き渡し条件だけ。
2. **詳細は担当資料へ出す**
   - 目的発見は `references/intent-discovery.md`
   - 再利用判断は `references/scope-and-reuse.md`
   - テスト先行は `references/test-first-workflow.md`
   - 保守・回帰判断は `references/maintenance-and-regression.md`
3. **テンプレートは契約の記録に限る**
   - 要件契約は `templates/requirements.md`
   - テスト契約は `templates/test-plan.md`
   - テンプレートは必要な案件だけで使い、常時読ませない。
4. **正本はリポジトリ内**
   - repo-local のスキルディレクトリを source of truth とする。
   - ユーザープロファイルへのコピーや同期は、このスキルの既定動作にしない。
   - 同期用 GUID パスや環境固有パスを成果物へ書き込まない。
5. **過剰設計を避ける**
   - 今回の責務を五つの参照資料と二つのテンプレートで表現できるなら、追加ファイルを増やさない。
   - 参考例や特定プラットフォーム API を汎用ルールとして埋め込まない。

## 設計承認で確認すること

- どのファイルが何の責務を持つか
- どの phase でどの資料を読むか
- 追加ファイルが本当に必要か
- 重複した guidance や同期前提が紛れ込んでいないか
